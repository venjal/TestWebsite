How the pieces fit

The exam is not “what does Copilot autocomplete.” It is “how do you give an agent a job, constrain what it can touch, watch it work, and prove a human stayed in the loop.”

Treat Copilot as three runtimes that share ideas but not the same files:

Cloud coding agent

Runs on GitHub. You assign an issue. It opens a draft PR, writes commits, and streams a session log. Steering happens with @copilot on that PR, from an account that can write to the repo.

Copilot CLI

Runs on your machine. Plan mode designs first. Autopilot / --yolo executes without prompts. Slash commands manage the token window. Hooks sit in front of tools.

IDE Chat / VS Code

Interactive. Context is the current chat plus open files. Custom agents, MCP, and instructions files still apply, but a new chat is how you drop stale turns.

GitHub Actions around the agent

Not the model. Environments, artifacts, concurrency, GITHUB_TOKEN permissions, CodeQL, and audit logs are how the platform enforces what the model is not allowed to ignore.

Mental model: prompts suggest, platform controls decide. If the stem wants a guarantee (cannot edit workflows, cannot see another repo, cannot approve its own plan, cannot keep logs two years on GitHub), the answer is almost never an instructions file.

Cloud coding agent

Background teammate on github.com. The issue is the spec. The draft PR is the workspace. The session log is the truth.

What it is

You assign Copilot to an issue (or start a task from the Agents panel). Copilot acknowledges with an eyes reaction, creates a branch and a draft pull request, and works in an ephemeral environment. When it is done it requests review. Everything it decided lives in the session log, not in the Actions runner log.

Knowledge you need

  • The issue body is the prompt. A one-line “fix login” issue produces an empty or off-scope PR. Fix the spec, do not add tools.
  • Status signals. Eyes on the issue = assignment accepted. Timeline “Copilot started work” = session is live. Draft PR with no Actions checks often means a human must Approve and run workflows.
  • View session on the PR is how you watch logs and see why it stopped or shipped zero files.
  • Steer without restart: comment on the open PR and mention @copilot. The author must have write permission. Copilot ignores comments on merged/closed PRs.
  • Restart a frozen session: official troubleshooting says unassign the issue and reassign it to Copilot. Sessions can sit still, then time out after about an hour.
  • CLI from a laptop: gh agent-task view <id> --log --follow tails the same session log.
Two different verbs. “Resume without redoing completed work” is View session + @copilot on the same PR. “Restart the frozen cloud process onto the existing draft” is unassign / reassign. Read the stem for resume vs restart.

Copilot CLI

Local agent loop with modes. The exam tests whether you can tell inspect, compact, plan, and autopilot apart.

MoveWhat it doesWhen you use it
/contextShows the token window: model, used vs capacity, system prompt, tools, history.You need to see usage. It does not free space.
/compactSummarizes older turns and replaces them with a structured recap.You need to continue the same session near the limit.
/usageSession stats / premium-request style counters.Billing-ish stats, not the context map.
/clearDrops history.You are willing to lose progress.
Plan modeReads the repo, writes a Markdown plan (plan.md), waits for approval.Complex work. Agree on the approach before any edit.
Autopilot + --yolo / --allow-allRuns without confirmation. Yolo = all tools, paths, and URLs.You already approved a plan and accept no human gates.

Plan mode is Shift+Tab in the interactive CLI, or an explicit plan-mode switch. After you accept the plan you can hand it to autopilot. Autopilot is local. /delegate is different: it ships the work to the cloud agent and a draft PR.

--max-autopilot-continues N is the runaway-loop ceiling. Without a cap, autopilot just keeps going. With --yolo there is no targeted human checkpoint.

Open editors in VS Code are implicit context. Stale Chat threads pollute answers. Cheapest fix: start a new chat and close unrelated files.

Custom agents

A Markdown persona with YAML frontmatter. Filename is not the identity. The YAML name is.

Where they live

  • Repo: .github/agents/*.md or *.agent.md — current project, current branch.
  • User: ~/.copilot/agents — every project on that machine.
  • Org / enterprise: /agents in the org .github or .github-private repo.

If the file is missing on the branch you checked out, the workspace agent is not in the picker. user-invokable: false hides it from humans. That is why a profile agent can exist and still not appear.

Frontmatter that the exam actually tests

KeyRule
tools:Optional allow-list. Omit the key to inherit every built-in and MCP tool. An empty array is still a list (usually nothing). Prompt text cannot enlarge a list.
agents:Whitelist of subagents a parent may start. Add the child to the caller’s list, not to a sibling.
disable-model-invocation: trueThe parent model may not start this agent as a subagent. Same idea as retired infer: false.
user-invokable: falseHumans cannot pick it from the dropdown. A parent can still invoke it unless model invocation is also disabled.
Handoffs + send:send: true starts a clean switch to the target agent. send: false keeps the same chat, so a “planner” can start implementing.

Planner / implementation-planner pattern: tools search, read, maybe fetch and docs MCP. No edit, no execute. Then a handoff labeled Start Implementation with send: true.

Handoffs vs cloud agent. VS Code handoff objects are documented for IDE agents. GitHub’s custom-agent reference notes that some IDE-only keys are ignored by the cloud agent on github.com. If a stem is about Chat in VS Code, handoffs matter. If it is about the cloud assignee, think issue + draft PR.

Model Context Protocol (MCP)

MCP is how the agent calls systems that are not the git repo: docs, ticketing, Sentry, internal APIs.

Three configuration planes

  1. Workspace / IDE: committed .vscode/mcp.json (or project MCP files). This is the “central for every developer on this repo” answer in a VS Code shop.
  2. Repo settings on GitHub: MCP JSON in repository Copilot settings. Applies to the cloud agent and Copilot code review. Not the same file as .vscode/mcp.json, same idea.
  3. Org policy + hosted MCP: policy turns servers on across Copilot surfaces. A GitHub-hosted MCP server is what you use when VS Code on a laptop and Chat on github.com must share tools with no local Docker.

Connecting a server advertises its tools, resources, and prompts. New tools on that server show up on the next session — unless the agent YAML still has a tight tools: allow-list. That is why “give agent1 all tools” and “configure MCP1” travel together: delete the allow-list, then attach the server.

Secrets

Cloud-agent MCP secrets live in the Copilot / Agents environment, not in Actions secrets and not in git. The name must start with COPILOT_MCP_. Reference that name from MCP JSON. Codespaces user secrets do not reach the cloud VM. A plaintext key in server.json fails the security requirement.

Default GitHub MCP token for the cloud agent is read-only on the current repository. Cross-repo access is a token-scope problem, not an instructions-file problem.

Hooks and execution policy

Hooks are deterministic shell. They do not “ask the model to be careful.” They run at a lifecycle point and can allow, deny, or log.

HookWhenExam use
preToolUse / pre-execBefore the tool or shell command runsBlock sudo, rm -rf /, curl | bash, paths outside the repo. Return JSON permissionDecision: "deny" or exit 1.
postToolUseAfter the toolToo late to stop rm -rf.
errorOccurredOnly when execution failsRun a shell command on failure. Not sessionEnd (that also fires on success).
sessionStart / sessionEndSession edgesBanners and logs. Not a command filter.
userPromptSubmittedEach user promptCan mutate or reject the prompt. Wrong tool for a single dangerous command.

Repo hooks: .github/hooks/*.json. CLI can also point at .copilot/hooks.yaml with cli.hooks.enabled: true.

Permission flags are a second layer: --allow-tool, --deny-tool, --allow-all, --yolo. Deny removes a tool. Require-approval (when the product exposes it) keeps the tool but stops for a human. Read the stem: “still available but needs approval” is not the same as “deny.”

Copilot memory

Repo-level facts Copilot learned and may reuse. Not a second git history.

  • Can be off for an organization. Several case studies start with memory disabled.
  • Delete paths: an admin / member deletes it in the UI, or it expires after about 28 days if it is not refreshed.
  • Just-in-time verification: before a memory influences a suggestion, Copilot checks that the cited code still exists on the current branch. If the snippet is gone (reverted, unmerged, other branch), the memory is ignored. That is how multi-branch / closed-PR noise stays out of suggestions.
  • Memories are not “deleted because the creating file was deleted” and not “wiped on merge.” Those are distractors.

Instructions, review guidance, and templates

Same idea — “tell Copilot how we work” — three different files with three different audiences.

FileAudience
.github/copilot-instructions.mdRepo-wide coding conventions for Chat / coding agent.
.github/instructions/*.instructions.mdPath- or surface-scoped instructions. Used when you need “apply this to all .md files” or a dedicated review checklist without changing every Chat turn.
.github/agents/*One persona. Does not automatically become Copilot code review policy. Some instruction files are explicitly excluded from code review.
.github/pull_request_template.mdHumans filling out a PR form. Not the reviewer model.

If the stem says “guidance for Copilot code review on every file,” look at the instructions paths, not the PR template and not a random agent file. Product docs still document both the classic copilot-instructions.md and the .github/instructions/ folder. Read the options; do not assume last year’s only path.

Actions, artifacts, environments, concurrency

This is the control plane around the agent, not the model.

Artifacts

actions/upload-artifact puts plan.md / trace.json on the run page (humans can download them) and actions/download-artifact hands them to later jobs on new runners. Caches are not a review UI. Committing generated plans into git is usually the wrong channel. Manual deletion of an artifact is audit event artifact.destroy.

Human-in-the-loop for plans and production

Create an Actions environment (example: plan-review). Add the security team as required reviewers. Do not add the developer team if the rule is “developers must not self-approve.” Job graph:

plan job  →  upload artifact
execute job  needs: [plan]
             environment: plan-review

Production secrets use the same idea: environment protection rules pause the job until a human clicks. Fully autonomous deploy of production-secret workflows fails separation of duties.

Concurrency

Workflow-level concurrency groups runs that should not overlap.

  • Same PR branch, many agent pushes: group: ${{ github.head_ref || github.run_id }} so each source branch has one live run, and non-PR events do not collapse into one global group.
  • Fan-out / fan-in: two jobs with no needs run in parallel; the merger job has needs: [job_a, job_b]. Concurrency is not fan-in. needs is.

Quality gates on agent PRs

Trigger validation with on: pull_request. Tests are a run: step (npm test in the Node examples). CodeQL is two official actions: github/codeql-action/init then github/codeql-action/analyze. Built-in security signals on generated code: secret scanning and CodeQL, not lint and not “median time to merge.”

GITHUB_TOKEN least privilege

permissions:
  contents: read          # workflow default is read-only
jobs:
  update_artifacts:
    permissions:
      contents: write     # only the writer job
      pull-requests: write  # only if that job opens a PR

Rulesets, CODEOWNERS, and token scope

When the agent keeps doing the wrong thing, stop asking it. Change what GitHub will accept.

  • Agent rewrites .github/workflows to skip failing checks. A branch ruleset that restricts that path. Instructions files are advisory.
  • Workflow and infra paths need named reviewers. CODEOWNERS names them. Branch protection or a ruleset makes those reviews required.
  • Protect main, still let the agent open PRs. “Require pull request before merging” on main. Do not ban the agent from feature branches.
  • Agent read files in a sibling repo. That is credential scope. A fine-grained PAT limited to product-api, stored as the agent’s secret, is an authorization boundary. A sentence in custom instructions is not.
  • Agent-only API token, Actions secrets banned. Copilot environment secret. Not git, not Actions.

Audit logs and long retention

GitHub Enterprise Cloud keeps native audit logs on the order of months (about 180 days) and Git events for days. Two-year retention is longer than that, so you stream the enterprise audit log to an external store. Azure Event Hubs is the Azure option the exam likes. “Configure retention” and “enable Git events” do not stretch native storage to two years.

Who deleted an Actions artifact: search the org audit log for action:artifact.destroy. PR comments and git history will not have it.

.NET Copilot app modernization

A packaged multi-agent flow for upgrading a legacy app (exam story: .NET 6 App1 → .NET 10).

FileRole
assessment.mdAnalysis: breaking changes, deprecated patterns, whether upgrade steps and tests look good. Humans validate this before a retry.
plan.mdHow the agent proposes to change code. Review it; do not treat it as proof the assessment is true.
tasks.mdWork items derived from the plan. Existence of the file is not a security gate.

Unsafe to fully delegate: signing off that the assessment is accurate (especially if it found a vulnerability) and approving Git commits. Generating the files is the agent’s job.

How the two case studies use these topics

Not questions. A map so a Contoso or Litware stem does not surprise you.

Contoso

repo1 portal (frontend + api) plus repo2 legacy App1. Learn MCP is allowed at the org but each developer wired it themselves — centralize with workspace mcp.json. agent2 is a planner: search + read, no edit. UI drift is a folder-structure instruction problem. Modernization retry starts at assessment.md.

Log trap: CLIMCPServerEnabled=false means the CLI MCP server is off even if the org registry is “on.” Count session IDs; do not invent servers.

Litware

Three repos, agent1 on product-api, agent2 on infra-terraform, MCP1 needs a key, memory off, SG_Dev vs SG_Review.

Scope leak → fine-grained PAT. Empty green PR → session log. All tools → delete the tools: line. MCP key → COPILOT_MCP_ Copilot secret. Plan approval → plan-review environment owned by SG_Review only. Shared file fights are either isolated branches + overlap checks (written guideline) or a concurrency group (some keys serialize the workflows). Know both stories.
